# Interrupted population experiments

Strict checkpoint recovery is opt-in with `provider_failure_policy.strict_recovery: true` in a population config. It currently supports one game per experiment. Set `--agents-root` to a path inside that experiment, such as `experiments/<experiment-id>/agents`; an external path is rejected before any folio or experiment files are changed.

A strict dry-run may create a `population_manifest.json` and `dry_run_report.json`. A later fresh launch recognizes that pair as preflight evidence, preserves the report, and replaces the manifest with the actual run plan.

Strict recovery prevents fallback or later game effects after an unresolved failure. Eligible received-invalid decisions may enter the configured correction flow; `repeat_with_feedback_v1` allows further exact-feedback corrections within finite shared budgets. Provider/transport ambiguity, budget denial and integrity failures remain halts. See [provider recovery](PROVIDER_RECOVERY.md) for default versus opt-in behavior. Monitoring is external and separately configured; no schedule or automatic authorization is installed by the runner. `--status` reads the recovery checkpoint and pending request decisions without starting play. `--request-halt` writes a durable cooperative marker checked before provider dispatch, message commit, adjudication, cleanup, and publication:

```powershell
python scripts/run_population_experiment.py --config path/to/config.yaml --output-root . --agents-root experiments/my-run/agents --status
python scripts/run_population_experiment.py --config path/to/config.yaml --output-root . --agents-root experiments/my-run/agents --request-halt --halt-reason operator_review
```

After reviewing the failure, resume explicitly. If a request was dispatched but no response was durably received, status reports its logical decision and attempt IDs. Prefer exact-original retrieval and validation. The CLI supports the following replacement action, but it requires separate authorization accepting a possible duplicate charge; a monitor's original-only policy does not permit it:

```powershell
python scripts/run_population_experiment.py --config path/to/config.yaml --output-root . --agents-root experiments/my-run/agents --resume --decision-action retry_unknown --decision-id <decision-id> --attempt-id <attempt-id>
```

`abandon_unknown` permanently abandons that logical decision. It does not substitute orders, continue past the halted phase, or remove the uncertain budget reservation. For a received-invalid response outside automatic correction, an authorized `retry_invalid` action binds the exact decision, rejected attempt and actual prompt hash (`--prompt-hash`). Do not repeat a consumed action or regenerate an accepted decision. Resume without a decision is allowed when no unresolved external request or rejected response requires a choice. The default three-request limit includes earlier dispatches and unresolved prepared requests; opt-in repeat corrections and exact historical exceptions are described in [provider recovery](PROVIDER_RECOVERY.md).

The runner stages the experiment tree, including prepared folios, and leaves the canonical game files unchanged while the game is incomplete. After interruption it replays from a hash-verified game-start snapshot, reuses received responses that match the exact country/decision occurrence and prompt hash, and applies the resulting phase effects into the stage once. This uses local CPU to replay earlier phases. Per-file hashes let a later resume finish a partially published final tree. The compatibility identity binds all installed package files, map data, model profiles, configuration, blueprints and prompt assets; code, data or prompt drift requires explicit diagnosis before resume. Provider attempts, budget reservations and recovery decisions live outside that staged tree and are never rolled back. The journal records local dispatch IDs and returned provider IDs when available; they help diagnose requests but do not establish idempotency or exact billing.

The separate monitor does not cancel an in-flight synchronous request; a synchronous request may continue remotely after the local client times out. Automatic remote-response retrieval and Responses background polling are deferred. A crash before the received response is durably journaled leaves an unknown outcome and requires the same explicit decision. Review the prompt and run records before choosing a recovery action. This process estimates configured cost exposure and cannot guarantee the vendor invoice.


## Reviewed relationship-capacity upgrade

The following named Luna migrations are historical, consumed recovery records. That experiment completed cleanup and reports on 2026-10-28; these commands must not be reapplied to it. They are not general migration recipes for new runs.

Negotiation and reflection support up to six relationship updates, covering the six other powers. New prompts and schemas use six; storage and legacy reflection conversion retain all six. Other message and lesson limits are unchanged.

For a halted run created under the earlier three-update code, `scripts/prepare_relationship_resume.py --config ... --agents-root ...` revalidates received responses offline and prints the exact predecessor/current identity hashes. It never runs game phases or calls providers. After reviewing those identities and the code change, add `--prepare --expected-before <hash> --expected-after <hash>` to append a bound compatibility approval. Preparation refuses config/data changes, pending unknown requests, skipped responses and unfinished publication. It preserves checkpoint/history backups and all request/budget evidence. Revalidation failure prevents approval.

An approved resume reconstructs the original prompt format only for saved decisions, verifies the original hash, and requires the cached response to exist. It evaluates those responses under the six-update contract; future decisions use the new prompt. Original invalid-validation records remain in the journal alongside the explicit revalidation approval. Preparation leaves the game halted: normal `--resume` remains a separate operator action. An offline copied-run replay can be stopped before its first new decision to prove completed requests are reused; it is not a live launch.

## Forced retreat disbands after an empty legal catalogue

The engine resolves an omitted retreat order by destroying the dislodged unit when no legal destination remains. The strict runner accepts that case only when its deterministic engine-map check finds no destination after active occupancy, standoffs and the dislodged attacker's origin are applied, including the engine's dislodgement-by-convoy exception. It does not use another retreating unit's destination as a blocker. A missing order with any available destination, or a malformed, illegal, duplicate or unknown order, still halts. The validation row remains `missing_retreat_order`; the adjudicator's forced-disband rule is unchanged. This corrects the strict-guard false positive introduced on 2026-10-18; it does not show that earlier non-strict runs were corrupt.

For the reviewed `luna1912-1018-r2` halt at `1902_spring_retreat`, first copy both the experiment directory and its sibling `.luna1912-1018-r2.recovery-work` stage into an isolated test root. The pre-fix package snapshot and response binding are under `experiments/retreat-fix-20261019/`. Run the copied game through the retreat with a test-only logical identity rebind and a provider that refuses every call; require the exact expected retreat resolution, the next uncached decision boundary, unchanged budget/provider-attempt bytes and no source-run writes. The checked proof is `experiments/retreat-fix-20261019/replay-retreat-proof.json`; it reports 147 cached decisions replayed, zero provider calls, and no legal retreat for France A Bel or Russia F Rum.

Only after offline replay and independent review should `scripts/prepare_retreat_resume.py` be considered on the original run. Supply the exact captured pre-fix `llm_diplomacy` package tree, experiment config and in-run agents root, plus the reviewed predecessor and target identity hashes from the binding and current configuration. Its dry run verifies package hashes, unchanged configuration/data identity, the prior six-relationship approval, halted phase, snapshot/journal integrity, no pending request/publication, and all seven saved empty retreat responses. `--prepare` appends one hash-bound journal receipt; it does not rewrite the checkpoint, prior validations, prompts, responses, attempts, budgets or metrics and makes no provider calls. The receipt preserves every received-response hash and every skipped-response ID. It approves only the seven existing false global retreat-validation rows; it does not unskip any response. Any code/package drift outside the two reviewed runner files, or any other state mismatch, must stop preparation. Historical rejection rows remain intact; the receipt lets strict recovery recognize only these exact saved receipts.

Replay a copied run with saved responses and a provider that refuses inference. Compare the full request ledger, budget files, journal prefix, response hashes and canonical retreat resolution before allowing the live owner to prepare or resume. The forced disband count may be worth a separate metric change; metrics currently retain the engine's rejected `missing_retreat_order` validation row, so automated reporting could continue to classify the forced disband as invalid player output. Do not rewrite historical metrics as part of this fix.

## Responses that complete after a network timeout

A synchronous HTTP timeout is not evidence that generation failed. Let the player finish: do not substitute orders, score a failure against the player, or generate a replacement merely because the client stopped waiting. The provider may still be processing the original request. Monitoring can run every 30 minutes while the game is paused; continued provider processing is not a stall. Keep the model, reasoning effort and game budget unchanged.

Use the signed-in provider project's Responses logs to locate the existing request by its start time and input. Client request IDs are the recovery attempt IDs sent in `X-Client-Request-Id`; provider support can trace them if the dashboard does not expose them. Preserve the observed response IDs, then use `scripts/recover_provider_responses.py --config ... --agents-root ... --manifest records.json --fetch` for GET-only retrieval. The manifest has a `responses` list containing each original `attempt_id` and observed `response_id`. For offline records, supply `response_path` and `input_path` and omit `--fetch`. If any response is queued or in progress, retrieval preserves its observation and returns without import; wait for the same response rather than retrying generation. Errors, missing/expired records or ambiguous matches need review.

The helper binds every recovered result to the original prompt SHA256, provider/model, request interval and unique original budget reservation. It requires all unknown attempts for that decision so duplicate completions cannot disappear from accounting. It validates the earliest original attempt against the current saved context and deterministically selects that answer, without choosing the most favorable output. Completed results, provider creation/completion timestamps, elapsed seconds, usage and unused duplicate outcomes remain recorded under `recovery/provider_imports/`. Add `--apply` after the check to settle the original uncertain reservations and append cached received responses under the exclusive writer lock. It never generates or starts the game. A durable transaction makes interrupted settlement/import idempotent; the actual request ledger and its original transport errors remain unchanged. These errors describe local transport outcomes, not player fallbacks. Receipts and budget state supply recovered usage separately; configured-price estimates do not establish the provider invoice or exact cached-input discounts.

After successful import, ordinary `--resume` reuses completed answers and continues with the next unfinished decision. Do not use `retry_unknown` or `retry_invalid` for a result already obtained. An existing three-request cap prevents further generation but does not prevent importing and replaying a completed result. Monitors may only apply and resume when the user has authorized that recovery workflow; they must preserve evidence and stop on validation, identity, integrity, credential or budget problems. This workflow tolerates long thought through later retrieval; it does not add asynchronous/background generation to the adapter.

Recovered usage also restores aggregate totals only after every actual request has complete, unambiguous usage and the reconstructed sums equal the known budget counters. This fixes sticky unknown totals without changing any limit or call count. `--reconcile-accounting` can finish that step for an earlier import. An exclusively unknown-cost false denial may be cleared only after this complete proof and a fresh limit check. Its exact synthetic blocked cache entry (never dispatched) is marked skipped; original rejection/history remains visible. Monitors must distinguish that preserved non-request from a new invalid player response. Missing usage, mismatched ordering, real exhausted limits or unrelated stop reasons fail closed.
